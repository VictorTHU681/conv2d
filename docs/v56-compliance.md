  源码注释中的 k39/k81 是说明实例，不是精确尺寸条件。运行脚本列四个尺寸是题目要求。

## 需要注意的边界

1. **HBM 放置不等于题面原始命令。** `run.sh` 默认增加 `numactl --preferred=<HBM>`，
   还设置线程绑定；历史记录显示用户已批准使用 HBM，但仓库题面没有主办方允许该参数的明文。
   当前 81×81 的 DDR +1.43% 是不增加 HBM preferred 参数的 v55/v56 对照；HBM +2.17% 是单列的额外内存放置对照。
   不把用户授权说成官方规则，也不混用两组性能。脚本已有 `CONV_HBM=0` 开关。
2. **诊断包不能与默认包的合规结论混同。** `conv_diag.zip` 通过 `mkdiag.py` 注入
   第 2 次调用的主频/FMOPA/带宽探针，并按调用序号调整诊断输出；`run_diag.sh` 还读取系统状态。
   这些是实际存在的诊断行为。它们不在正式 `conv.zip` 中；若约束禁止评测环境探测或依赖调用阶段，
   诊断包不满足该约束，不能作为正式提交。正式实现和性能结论以 `conv.zip` 为准。
3. **非默认并行打包存在数据竞争。** `CONV_PACKSER=0` 时，`roll_pack_all` 允许多个线程
   重做尚未完成的同一 chunk，非原子写相同 float 仍存在并发写/读写竞争；done 原子标志不互斥保护
   chunk 的内容。默认 `pack_ser=-1` 被解析为串行打包，避开该路径。
   这是源码层面的正确性问题，不是已经观察到的默认版错误；该可选路径需要互斥认领/等待后才能推荐。
4. **通用库健壮性仍有缺口。** 全局计划、缓冲和线程池没有顶层调用锁，不能承诺多个调用者同时调用
   `conv2d` 安全；滚动准备中的若干分配返回值未经检查，低内存下可能解引用空指针；SME 汇编固定
   64 字节向量步幅，入口没有验证 streaming vector length，不能承诺其他 SVL 的硬件可用。
   题面单进程顺序调用和已测服务器没有触发这些限制，本次不把它们归类为已证实的赛题违规。

## 后续复查及已完成修复：首行前缀越界读取

复查 `fill_args`（约 1228、1240 行）确认：输入首地址未按 64 字节对齐时，
首行初始化会先向下对齐，再复制包含对齐前缀的范围，从而读取输入对象之前最多 60 字节。
这些字节不参与有效计算，但“结果正确”不能消除超出输入对象边界读取的问题。
这是原 v56 从 v55 继承的问题，初次审查和此前的结果校验没有覆盖到；现已修复。

修复候选改为从真实 `P->in_row` 复制到 `ring + sh`，长度只包含有效输入。
独立诊断记录每次首行拷贝的源区间，用原版作为必须能检出的阳性对照，修复版必须零越界区间，
并检查全部 16 种 float 对齐偏移的逐位结果。详见
[first-copy.md](v56-experiments/first-copy.md)。运行时诊断在原版发现 255 次超出输入范围的请求，
修复版为 0，96 项输出均逐位一致。修复版随后通过 849 项额外验收、72 次三方官方校验及
三个包共 12 次完整校验，已成为当前本地 v56。该诊断只覆盖首行 helper 的读取区间，不代表所有汇编访问都已被动态检查。
