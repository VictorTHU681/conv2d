## Packing reuse regression

Code inspection found that `roll_groups(..., P->G)` overwrites allocated buffer
pointers with null initializers on each changed kernel, preventing reuse and
losing the old allocations. The candidate preserves each group's allocation
pointer and capacity while replacing its shape metadata. It also treats the
kernel-copy size as a capacity (`>= kn`), allowing a smaller unchanged kernel to
be recognized after a larger kernel was processed.

`tools/test_pack_reuse.c` wraps aligned allocations and frees, repeatedly cycles
81/39/39/55 kernels (including changed coefficients), compares every output
bitwise with ordered `fmaf`, and requires no more aligned allocations after the
first complete cycle. Baseline is an expected failing allocation control.
Job `1579543` completed on cn20481 at 18:00:23 +08:00. Both versions produced
bitwise-correct outputs for all 32 calls. Baseline had 91 extra aligned
allocations after the first shape cycle and reached 212 MiB live aligned
storage; the candidate had zero extra allocations and stayed at 12 MiB.
These counts cover the wrapped aligned buffers, not the process's total RSS.
Raw evidence: `results/v52/cache.log`; its baseline allocation FAIL is the
deliberate negative control, followed by the fixed candidate's PASS.

## Additional candidates

- `copy2/copy4`: unroll the input-row ring copy, consolidate address increments;
  do not change loaded elements or accumulation order.
- `done/donecopy2`: replace the pool's shared completion RMW counter with one
  release-store generation per worker and acquire-load joins in the caller.
  The latter candidate also includes the two-vector copy loop.
- Scheduling weights: single16 1.04/1.06 and K4 1.15/1.30 versus the defaults
  1.02/1.23. These affect work partitioning, not arithmetic.
